FIX 1 — ROAD TEST TRUTHFULNESS
CRITICAL
==================================================

AUDIT FINDING:

The guided inspection path currently writes a generic string such as:

"Wizard submission — see inspection steps"

into test_drive_notes.

When structured road_test_module data is absent, report-generation fallback logic can interpret a sufficiently long test_drive_notes value as evidence that a road test occurred.

This can incorrectly produce:

- Road Test Completed
- Road Test Observed
- transmission assessed
- removal of "road test not performed" from missing information
- potentially improved completeness/confidence

This must stop.

RULE:

A road test may be represented as COMPLETED only when the system has explicit evidence that a road test was actually completed.

Preferred authoritative statuses:

completed
not_permitted
not_possible
not_performed / unavailable if currently supported

Do NOT infer road-test completion from:

- generic notes
- string length
- inspection completion
- mechanical notes
- transmission observations
- existence of test_drive_notes

IMPLEMENTATION REQUIREMENTS:

1. Locate every place report scope determines whether road testing occurred.

2. Remove generic text/note-length inference.

3. Structured explicit status must be authoritative.

4. If no structured road-test status exists:

   Road Test = Not documented / Not performed

   Use terminology consistent with existing RideCheck architecture.

5. "not_permitted" must remain explicitly represented as seller not permitting the road test.

6. "not_possible" must remain explicitly represented as road testing not possible because of location, condition, safety, or other recorded reason.

7. Absence of a road test must appropriately affect missing-information/completeness logic.

8. Do NOT penalize the vehicle itself because a road test was unavailable.

9. Transmission must NOT be described as road-test assessed unless the road test actually occurred and relevant observations were recorded.

10. Remove or replace the guided wizard's generic test_drive_notes placeholder if it can create downstream ambiguity.

TESTS REQUIRED:

A. structured status = completed
Expected:
Road Test Completed.

B. structured status = not_permitted
Expected:
Not permitted by seller.
Never "completed."

C. structured status = not_possible
Expected:
Not possible/performed.
Never "completed."

D. road_test_module absent + generic notes present
Expected:
Never "completed."

E. no road-test information
Expected:
Missing/limited information appropriately reflects that no road test was documented.

FIX 3 — HUMAN CONFIRMATION BEFORE AI-EXTRACTED DTC
INFLUENCES BUYER REPORT
==================================================

The extraction engine assists the RideChecker.

It is NOT authoritative evidence by itself.

CURRENT GOOD BEHAVIOR TO PRESERVE:

confidence < 60:

codes: []

and extracted candidates remain low-confidence rather than automatically populating the normal DTC list.

DO NOT weaken that behavior.

NEW/VERIFIED REQUIREMENT:

AI-extracted DTC codes must be reviewed/accepted by the RideChecker before they can influence:

- Claude report interpretation
- buyer-facing OBD findings
- repair-cost context
- significant findings
- report narrative

Use the smallest implementation compatible with the current UI.

If the current "Extract codes with AI" workflow already presents extracted codes for inspector review, determine whether an explicit accepted/reviewed state already exists.

Do not add unnecessary workflow if it already exists.

If no durable review state exists, add the smallest appropriate field/state such as:

reviewed / accepted

or equivalent consistent with the existing architecture.

IMPORTANT:

Do NOT force manually entered codes through AI confirmation.

Manual code entry remains source = manual.

LOW CONFIDENCE:

confidence < 60 must NEVER automatically become accepted diagnostic evidence.

Also inspect the audit finding that low-confidence extraction may still populate:

- scanner identity
- aggregate emissions status

Scanner identity may be retained as tentative metadata if appropriate.

But low-confidence extracted diagnostic assertions must not silently influence buyer conclusions.

If confidence is inadequate, preserve uncertainty.

FIX 4 — REMOVE PURCHASE-DECISION MAPPINGS
CRITICAL PRODUCT PRINCIPLE
==================================================

AUDIT FINDING:

The report-generation route still contains internal recommendation mappings such as:

BUY
BUY_WITH_NEGOTIATION
DO_NOT_BUY_AT_ASKING_PRICE

These conflict with RideCheck's operating principle even if they are currently internal.

RideCheck does not decide whether the customer should purchase a vehicle.

REMOVE purchase-decision mappings from the report pipeline.

Do not replace them with disguised recommendations such as:

GOOD BUY
BAD BUY
SAFE TO BUY
AVOID
WALK AWAY
RECOMMENDED PURCHASE
NOT RECOMMENDED
BUY IF...
PASS

RideCheck may communicate:

- observed condition
- evidence
- HIGH / MODERATE / LOW risk
- financial exposure
- inspection completeness
- missing/unverified information
- price/condition context
- buyer considerations

The buyer makes the decision.

If a database field such as ops_recommendation cannot safely be removed because of schema compatibility:

Do NOT perform a risky migration for this stabilization.

Instead:

- stop generating purchase-decision values;
- neutralize/deprecate the field in application logic;
- confirm it cannot influence the buyer report or downstream workflow;
- document the remaining schema debt.
