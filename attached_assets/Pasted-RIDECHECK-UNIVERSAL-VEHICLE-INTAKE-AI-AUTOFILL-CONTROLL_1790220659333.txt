RIDECHECK UNIVERSAL VEHICLE INTAKE + AI AUTOFILL
CONTROLLED IMPLEMENTATION — IMPROVE THE EXISTING BUYER BOOKING FLOW

OBJECTIVE

Improve RideCheck's EXISTING buyer booking experience so a buyer can give RideCheck whatever vehicle information they already have and RideCheck does as much of the data entry work as safely possible.

Core buyer experience:

“Found a vehicle? Send us what you have.”

A buyer should be able to start with:

1. a vehicle listing URL
2. listing screenshots/photos
3. dealer window sticker / vehicle information photo
4. roadside FOR SALE sign / vehicle photo
5. manual vehicle details

RideCheck should extract available information, show the buyer what was found, allow confirmation/correction, and then populate the EXISTING booking fields.

This is NOT a new booking system.

Do not rebuild:

- order creation
- server-authoritative package classification
- pricing
- Stripe checkout/payment
- seller coordination
- Facebook buyer bridge
- Communication Center
- RideChecker compensation
- dispatch
- inspection
- QA
- reports
- payouts

Extend the current booking flow safely.

The existing booking audit established:

- current booking has 3 wizard screens
- normal Concierge flow has 7 required typed fields
- package classification is already server-authoritative
- listing URLs are currently stored but not parsed for vehicle data
- no existing buyer-facing screenshot/photo intake exists
- existing RC photo upload is NOT appropriate for buyer intake
- Buyer Arranged currently sends some fields that are not persisted
- seller type and discovery source are distinct concepts
- mileage and asking price can affect classification
- vehicle location and service ZIP serve different purposes

Preserve those realities.

════════════════════════════════════
NON-NEGOTIABLE PRODUCT PRINCIPLE
════════════════════════════════════

DO NOT turn this into a longer AI form.

The purpose of AI is to REMOVE buyer work.

The desired experience is:

Buyer gives RideCheck what they have
→ RideCheck extracts what it can
→ RideCheck shows what it found
→ buyer confirms/corrects
→ RideCheck asks only for missing information actually required
→ existing booking/payment flow continues

Never make the buyer fill the same information twice.

Never require AI extraction to complete a booking.

Manual entry must always remain available.

Extraction failure must NEVER block booking.

Unknown information must remain UNKNOWN.

Never invent:

- trim
- mileage
- price
- VIN
- location
- seller type
- seller contact information
- vehicle specifications

Do not use model knowledge to fill missing listing facts.

PART 7 — AI EXTRACTION SERVICE
════════════════════════════════════

Implement a bounded vehicle-listing extraction service.

Use the currently configured AI infrastructure if it safely supports image input + structured output.

If OpenAI is already configured and appropriate, use the current Responses API with a vision-capable model appropriate for structured extraction.

Prefer a cost-conscious model suitable for extraction rather than automatically using the most expensive model.

If another production AI provider is already canonical in RideCheck and provides equivalent reliable image + structured extraction, do not introduce unnecessary provider duplication.

The extractor is a FORM-FILLING ASSISTANT.

It is NOT the authoritative vehicle database.

Return structured data.

Target fields:

{
  year,
  make,
  model,
  trim,
  mileage,
  asking_price,
  location_text,
  service_zip,
  vin,
  seller_name,
  seller_phone,
  discovery_source,
  platform_source
}

For EACH extracted field, preserve provenance.

Example internal structure:

{
  "mileage": {
    "value": 172000,
    "source_type": "uploaded_image",
    "source_reference": "...",
    "evidence": "172K miles"
  }
}

Evidence should be concise.

Do not require a fake universal confidence percentage.

If confidence is useful internally, it may be recorded, but provenance/evidence is more important.

STRICT EXTRACTION RULE:

Only return a value when it is explicitly supported by the supplied material.

If unavailable:

null

Never infer missing listing facts from general automotive knowledge.

Example:

If image says:

2013 Mercedes-Benz S 550
172K miles
$11,000
Hoffman Estates

valid extraction:

year = 2013
make = Mercedes-Benz
model = S 550
mileage = 172000
asking_price = 11000
location_text = Hoffman Estates

If trim or VIN is not visible:

trim = null
vin = null

DO NOT guess.
